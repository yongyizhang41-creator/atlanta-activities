# Atlanta Activities — 第一版设计

日期：2026-10-22。状态：用户已确认，进入实施计划阶段。本文是需求与架构设计，不表示功能已实现。

## 1. 目标和已确认范围

建设面向公众上线的活动发现网站。用户最新确认：当前优先完整实现所有需求，技术栈和技能学习推迟到全部功能完成之后，不在开发阶段安排教学。界面使用英文；开发说明使用中文。活动覆盖 Downtown Atlanta、Midtown 和 Georgia Tech 校园的重大集体娱乐活动，包括体育比赛、游行、演出、节庆和校园活动。第一版不实现购票或报名，链接到原始来源。

用户必须登录后访问活动功能。支持邮箱密码注册登录、邮箱验证、密码重置和 Google 登录。校园活动无论是否向公众开放均可收录，但明确标注参与资格；未注明时显示 Eligibility unconfirmed，不推断为公众开放。

采用自动收集、自动校验后直接展示。取消人工审核和 Admin 页面。“所有重大活动”是产品覆盖目标，不承诺覆盖全网；实际收录范围由已接入来源、地域与收录标准决定，页面公开来源和更新时间。

## 2. 页面与核心流程

### Explore

登录后默认打开 Explore，提供 This week / Next week，显示具体日期。周次统一以 America/New_York 时区计算，周一 00:00 到下一周周一 00:00，采用左闭右开区间。夏令时使用时区规则，不能用固定 UTC 偏移计算周界。

本周默认只展示尚未结束的活动，进行中的活动标注 In progress。跨周活动只要与所选周重叠且尚未结束即可展示。缺失结束时间时，仅在开始前展示；开始后显示在个人看板中并提示结束时间未知，不推断仍在进行。

活动类型多选采用 OR，类型条件与周次、地理条件采用 AND。未选择类型表示全部类型。切换周次保留其他筛选条件。地图与列表使用相同查询和结果；空结果、加载中、失败重试都有明确状态。

每项活动显示标题、开始和结束时间、地点、类型、参与资格、已知票价和报名要求、来源链接、最后同步时间及取消状态。未知信息明确标注，不编造。详情提供 Ask AI、加入 Maybe 或 Going 的操作。

### My Plans

看板两列：Maybe（备选）和 Going（即将参加）。活动卡片可拖动，提供等效按钮供移动设备和键盘操作；支持列内排序。首次加入 Maybe 或 Going、切换列和移除均保存到账号，同一活动每个用户只能有一张卡片。看板跨周保留，不受 Explore 筛选影响。

已结束或取消的活动继续保留并显示状态，禁止新建提醒。第一版不自动删除历史卡片，也不提供外部日历同步。

## 3. 地图与地域查询

前端地图支持活动标记与聚合、点击查看活动、定位用户、半径筛选，以及绘制、清除和重画单个多边形。具体地图服务商在实施计划前按可用性、授权和成本确定，本文不预设已开通任何服务。

地理筛选有三种状态：无地理限制（仍限产品覆盖区域）、Radius、Draw area。Radius 和 Draw area 互斥；切换模式清除另一种模式的查询条件。Radius 以 miles 为默认显示单位，传给 API 时转换为 meters。允许 0.1–50 miles 的半径，并提供快捷值。用户主动请求定位时才申请浏览器权限；拒绝或失败时可在地图上手选中心点。不要求后台持续定位。

活动坐标使用 WGS84，PostGIS geography(Point,4326) 计算半径距离，边界包含在内。圈选 API 接受有效 GeoJSON Polygon，坐标顺序为经度、纬度；限定单个简单多边形、最多 200 个顶点，拒绝自交、无效坐标与过大的请求。使用 ST_Covers 语义包含多边形边界。无论筛选条件如何都与产品覆盖区域相交。

覆盖区域由版本化 GeoJSON 边界配置定义，而不是按活动文案猜测。Downtown、Midtown、校园的具体边界和地理编码结果须在接入数据时核验。游行等路线活动第一版用来源提供的集合点或起点作为标记，并明确这是代表位置；不绘制完整路线。缺少可靠坐标的活动不进入公开列表。

## 4. 自动活动采集

每个来源有独立适配器，共享规范化、验证、去重、地理编码和入库流程。优先选择可合法读取的官方活动日历、结构化 feed/API 和场馆公开信息；遵守来源访问规则。具体初始来源清单必须在实施计划前核验，不能把未经验证的 URL 当作已接入来源。

仅收录有明确时间、地点和集体参与性质的娱乐活动；排除普通营业时间、私人聚会和仅线上活动。校园活动保留资格限制；不以 AI 单独判断活动事实。采集覆盖本周、下周，并持续刷新个人看板中未来活动的状态。

默认每 6 小时运行一次，所有采集任务幂等。来源内以稳定外部 ID 去重；跨来源通过标准化标题、场馆、开始时间识别高置信重复项，不能确定时保留独立记录。重复合并时保留来源映射、稳定活动 ID，并合并用户看板引用，避免丢失提醒。单个来源失败不阻断其他来源，不清空已有活动。

公开前验证标题、可解析开始时间、可信地点与坐标、地域归属和来源链接。无结束时间可以收录但明确显示未知。校验失败的记录保留在内部采集日志中供开发排查，不提供人工审核队列。重复系列活动按每场 occurrence 建立独立活动。

检测到改期时更新活动版本、重算冲突、取消未发送提醒，并在看板提示重新设置。取消活动时保留取消状态、停止提醒。来源暂时消失不直接视作取消；保存最后成功同步时间，连续 24 小时未成功核实则显示资料可能过时。

## 5. 时间冲突检测

只检查同一用户 Going 列中的未取消活动，不计算交通时间。已知结束时间的区间采用 [start,end)，两活动满足 startA < endB 且 startB < endA 才冲突，因此首尾相接不冲突。

加入或移入 Going 时，后端返回冲突活动、各自时间及重叠时段，前端提供 Add anyway / Keep in Maybe。首次操作若有冲突不完成 Going 写入；用户确认后再次提交，后端按最新数据复查。并发操作按用户串行化，避免两个浏览器标签同时加入时绕过检测。确认针对本次最新冲突集合，集合变化则重新提示。

用户确认后允许保留两个活动，均可设置提醒，卡片持续显示冲突标记。从 Maybe 进入时取消则留在 Maybe；从 Explore 直接加入 Going 时选择 Keep in Maybe 则保存至 Maybe。缺少结束时间时提示 Cannot fully check conflicts，要求确认后才加入，不自动估计时长。移除、切换列、改期或取消后重新计算标记。

## 6. 单次邮件提醒

仅 Going 中的未取消且尚未开始活动可设置提醒。每个用户每个活动最多一封活动提醒邮件；发送后不可再创建第二次。发送前允许修改或取消。

快捷选项：1 day、3 hours、1 hour、30 minutes before；无效选项禁用。也可选自定义当地时间。浏览器和后端均要求 now < remind_at < event.start_at，保存 UTC 时间，展示 America/New_York。遇到夏令时重复或不存在的本地时间，UI 要求明确可用时间及偏移，不静默猜测。

移回 Maybe、移除活动、活动取消或改期时取消待发送提醒；重新进入 Going 后允许重新设置，但已发送过的活动不重发。移除再加入不能绕过发送次数限制，因此保留独立发送历史。

独立 worker 每分钟领取到期任务，发送前检查 Going 状态、邮箱验证、活动状态与版本。已过提醒时间但活动尚未开始的延迟任务立即处理；已开始的活动不补发。任务使用数据库锁和原子状态转换，具有重试次数、退避和失败日志；邮件服务支持时传入幂等键。不能承诺跨外部邮件服务严格 exactly-once，提供者超时导致结果未知时先查询或依赖幂等机制，避免盲目重发。

提醒发往账号的已验证邮箱。创建提醒时明确告知收件地址；未验证时引导验证。Google 账号邮箱也必须依据提供方的 verified 标志判断。

## 7. AI 活动问答

聊天绑定单个活动，只允许访问当前用户自己的会话。FastAPI 在服务器调用 OpenAI，传入该活动的规范化资料、来源和最后更新时间。模型回答活动事实时必须依据提供资料；缺失票价、资格、无障碍设施等信息时明确无法确认并提供来源。

默认不实时联网搜索，不承诺回答来源没有的信息。AI 跟随用户提问语言，UI 保持英文。用户问题和采集文本视为不可信内容，不能改变系统指令，也不能直接触发看板、邮件或数据库操作。密钥只在服务端保存，不传给 Next.js 浏览器包。

限制单次输入长度、上下文长度、每用户调用频率和总预算；模型通过配置选择。AI 不可用时活动浏览、看板和提醒仍可使用，聊天显示可重试错误。聊天保存最少必要记录，用户可删除自己的会话；不把精确位置或密码发给模型。

## 8. 账号与权限

邮箱密码登录采用成熟密码哈希与会话实现，注册、重置和验证 token 需有有效期、单次使用和频率限制。会话使用 Secure、HttpOnly cookie；状态变更具备 CSRF 防护，CORS 仅允许配置的前端域名。所有资源查询按服务端 session 的 user_id 授权，不信任请求体提供的用户 ID。

Google 使用标准 OAuth/OIDC，检查 state、nonce 和 PKCE；使用稳定 provider subject 标识账号。若 Google 邮箱与现有密码账号相同，不仅凭邮箱自动合并：要求登录已有账号后明确绑定。提供退出和解绑流程；解绑后至少保留一种有效登录方式。

定位仅用于当次筛选，默认不存为用户位置历史。上线提供简明隐私说明和账号删除入口；删除账号后取消提醒并删除个人看板、会话及相关身份数据，运维日志不记录敏感 token 或完整位置。

## 9. 技术架构与数据模型

已选技术：TypeScript + React + Next.js；Python + FastAPI；PostgreSQL + PostGIS。Next.js 负责界面，所有业务规则由 FastAPI 执行。初始部署使用同源 /api 代理以简化 cookie 和跨域配置。数据库迁移使用 Alembic，数据访问使用 SQLAlchemy，并接入 PostGIS 类型。

单仓库建议结构：apps/web、apps/api、docs。API 与后台 worker 共享 Python 领域服务；数据库任务表支持采集与提醒，第一版无需额外引入 Redis。生产包含 web、API、worker、PostgreSQL/PostGIS 和 HTTPS；web 进程内计时器不能替代持久化提醒任务。

主要数据实体：

| 实体 | 关键内容与约束 |
| --- | --- |
| users / identities / sessions | 验证邮箱、密码哈希或 provider subject、会话与绑定关系 |
| sources / source_runs | 适配器配置、采集结果和最后成功时间 |
| events / event_sources | 稳定 ID、每场时间、状态、版本、参与资格、来源映射 |
| venues / event_categories | 地点名称、地址、坐标；活动可属多个分类 |
| user_event_plans | user_id + event_id 唯一、Maybe/Going、排序值 |
| reminders / reminder_deliveries | 到期时间、状态、事件版本、幂等键、发送与失败记录 |
| chat_sessions / chat_messages | 用户、活动、消息与来源上下文版本 |
| ingestion_jobs | 可领取、可重试的持久化后台任务 |

所有业务时间存 timezone-aware UTC；地点建立空间索引，活动时间、用户看板和待发送提醒建立相应索引。排序值更新必须验证卡片归属；看板写入使用版本检查避免覆盖较新操作。

## 10. API 边界

| API 组 | 职责 |
| --- | --- |
| /auth/* | 注册、登录、退出、验证、重置、Google 回调与账号绑定 |
| GET /events、GET /events/{id} | 周次、分类、半径或多边形条件、分页和详情 |
| /me/plans | 获取看板、加入、切换状态、排序、移除及冲突确认 |
| /me/plans/{event_id}/reminder | 创建、修改、取消、读取提醒状态 |
| /events/{id}/chat、/me/chats/* | 活动问答和个人会话管理 |
| /me/account | 账号信息、身份管理、账号删除 |

活动查询返回统一的筛选结果与总数；地图分页或聚合必须覆盖同一结果集，不能仅把列表第一页当作全部地图点。对复杂多边形查询可使用 POST /events/search，语义与列表查询一致。错误返回稳定 code 和英文提示；冲突响应携带可供用户确认的结构化信息。

## 11. 验证与上线标准

自动化验证重点：周界及夏令时；距离与圈选边界；分类组合；采集幂等和去重；时间区间冲突与并发确认；提醒有效时间、改期取消、重试和重复发送保护；账号授权隔离和身份绑定。

浏览器验收覆盖邮箱与 Google 登录、拒绝定位、空筛选结果、地图与列表联动、拖动和按钮切换、冲突确认、快捷及自定义提醒、AI 缺失资料回答和服务故障。上线前使用真实来源样本检查坐标、时区、资格与来源链接，并向测试邮箱验证定时发送。需检查桌面和手机布局、键盘操作、焦点和地图之外的等效列表操作。

上线必须具备持久化数据库与迁移、worker 健康检查、采集新鲜度和提醒失败监控、数据库备份、环境变量管理及真实邮件域名配置。Google、OpenAI、邮件、地图和地理编码服务尚未配置；实施计划须记录选定供应商和必需凭据，不能将 mock 成功视作真实集成成功。

## 12. 分阶段交付

1. 基础结构与活动发现：数据库、真实来源适配器、周次查询、列表地图和地理筛选。
2. 账号与个人看板：两种登录、权限隔离、拖动排序和冲突检测。
3. 持久化提醒：时间设置、邮件服务、worker、状态变化与重试。
4. 活动 AI 问答、端到端验证和上线配置。

每阶段提供可运行结果，以完整实现需求为目标；教学推迟到所有功能齐全之后。开发阶段可以使用明确标注的 fixtures，但公开上线前必须切换真实数据和服务。第一版不包含 Admin、人工审核、购票、外部日历同步、多次提醒、路线导航或交通时间冲突计算。

## 13. 设计自查与下一步

本设计已统一自动发布与改期处理，区分 Explore 周筛选与跨周看板，明确未知结束时间、位置权限、冲突确认和邮件发送边界。初始来源、地图/地理编码与邮件供应商尚未选定，是实施计划前的具体集成选型工作，不代表已接入。具体地域边界须随来源核验，不能声称覆盖全部重大活动。
